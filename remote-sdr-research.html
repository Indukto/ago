Research brief · Remote SDR & LoRaWAN

Remote SDR software, and how it fits the proposed LoRaWAN network

A desk-research survey: what "Remote SDR" actually means in 2026, which open-source projects are real, whether a general-purpose SDR can serve as a LoRaWAN gateway, and how the ChirpStack / balenaOS / TTN plan holds up. Every material claim is sourced; uncertain points are flagged.

Compiled 2026-10-13 · sources: GitHub, project docs, Semtech/EPFL/Packet Broker documentation · 4 parallel research passes
00

Bottom line up front

Remote SDR — pick
There are two distinct problems hiding under one name.
Device sharing (rtl_tcp, SoapyRemote, SpyServer) forwards raw IQ to a desktop client. Remote listening (OpenWebRX+, KiwiSDR, WebSDR) processes at the antenna and serves many independent listeners over a browser. Pick per use-case, not per project popularity.
Best open-source pick
OpenWebRX+ for a public web receiver; SoapyRemote for private device sharing.
OpenWebRX+ (AGPL-3.0, maintained, Raspberry Pi 64-bit images, built-in decoders, users, chat, scanning). SoapyRemote is hardware-neutral across RTL-SDR/Airspy/SDRplay/HackRF/Lime/USRP/Pluto.
SDR as a LoRaWAN gateway?
No — not for production. Keep the SX1302 concentrator.
SDR + gr-lora_sdr decodes one LoRa waveform well and is excellent for monitoring. It cannot replicate 8 parallel channel detectors × 8 SF demodulators, and no maintained SDR→Semtech-UDP/Basics-Station bridge exists. SDR is a complement, not a replacement.
Two flaws in the proposal
The packet multiplexer is UDP-only, and openBalena is still beta.
chirpstack-packet-multiplexer does not speak Basics Station (a request was closed as out of scope), so it cannot multiplex a modern Basics-Station gateway to two backends. openBalena remains self-hosted and "perpetually in beta".
01

The remote SDR software landscape

The single most useful distinction is where the DSP runs. That one question determines bandwidth, multi-user capability, CPU cost, and security posture.

Model A — raw transport

The server is a thin shim: it ships IQ samples and accepts tuning commands. All demodulation happens on the client, which must run desktop SDR software.

  • Bandwidth scales with sample rate — hundreds of kB/s to MB/s per client.
  • Usually a single shared tuner: one user retuning changes it for everyone.
  • Typically no authentication and no encryption.
  • Examples: rtl_tcp, SoapyRemote, SpyServer, RSP TCP Server.
Model B — server-side processing

The server demodulates and extracts a narrow channel per listener. Clients only need a browser.

  • Bandwidth drops to audio + waterfall — tens of kB/s per user.
  • Independent tuning per user is the whole point.
  • HTTPS, accounts and rate limits are the front door.
  • Examples: OpenWebRX+, KiwiSDR, WebSDR, no-sdr.

Deployment recommendations by scenario

Headless Pi streaming an SDR
  • Browser users, open stack → OpenWebRX+ behind HTTPS/reverse proxy, admin restricted.
  • Desktop SDR clients, simplest → rtl_tcp, treated as a private shared-control endpoint. Add rtlmux only to clone one stream.
  • Polish + bandwidth-aware → SpyServer (proprietary): ARM builds, reduced-IQ mode, many clients.
Low-bandwidth WAN / VPN link
  • Never forward full-rate raw IQ over a slow link.
  • Prefer SpyServer reduced-IQ, or no-sdr at ~12–13 kB/s/client, or OpenWebRX+ for listening/decoding.
  • A VPN protects the link but does not reduce bandwidth.
  • Do not expose bare rtl_tcp/rtlmux/gqrx rigctl to the internet.

Exposing a receiver: security and German legal context

This matters directly for a research institute (Institut für Seenforschung) that may publish a receiver, and it is the part most likely to be challenged in a presentation.

The core legal asymmetry

Receive-only is not the same as non-public. Germany's § 5 TDDDG ("Abhörverbot") permits taking cognizance only of messages intended for the operator, for radio amateurs, for the general public, or for an indeterminate group. For anything else, neither the content nor the fact of reception may be communicated to others — even if received unintentionally.

The written text does not answer the two questions a public WebSDR raises: is the remote listener also "taking cognizance", and does exposing tuning amount to communicating the content or the fact of reception? An October 2021 FragDenStaat request put exactly this to the BNetzA and was still showing "Warte auf Antwort" when checked. That is evidence of an open legal debate, not a ruling either way.

What is reasonably clear

  • A receive-only SDR emits no radio transmission, so the amateur-radio and frequency-assignment rules (AFuG admission, BNetzA frequency assignment) do not obviously bite. No WebSDR-specific permit was found. That is not an official blanket exemption.
  • An amateur licence (DL1xxx, DN9xxx) governs transmitting and operating an amateur station — it neither licenses a website nor overrides § 5 TDDDG.
  • TKG § 5 notification applies to commercially operating public telecom networks/services. A free, non-commercial research receiver is not obviously such a service; fact-specific if it ever becomes commercial.
  • If the setup can key a transmitter, it is a different compliance question entirely — do not expose transmit capability as if it were receive-only.

Data protection (GDPR / DSGVO)

Live audio is not automatically outside the GDPR: a callsign, voice, location or decoded telemetry can be personal data, and server logs/IPs certainly are. GDPR compliance also does not cure a § 5 TDDDG problem — the two are separate. For an institute, the practical guardrails are: scope the receiver to specific research bands and public/intended traffic rather than open-ended tuning; avoid recording raw IQ or audio unless the research question requires it; prefer transient processing plus aggregated or irreversibly anonymised output; and set short retention/deletion periods. Document purpose, Art. 6 legal basis, data categories, retention, access controls and any transfer outside the EEA, and have the DPO assess whether an Art. 35 DPIA is warranted.

Security: never publish the raw control ports

  • rtl_tcp, SoapyRemote, rigctld/rigctl and gqrx control are unauthenticated and unencrypted by design (SoapyRemote's maintainer discusses the lack of security/permissions directly; Hamlib documents a plain TCP text command interface).
  • Keep the SDR and every raw control port on an isolated VLAN/host. Give staff and collaborators a VPN with per-user accounts and MFA; firewall the raw protocols to VPN addresses only.
  • If the public needs access, expose only a purpose-built web receiver through a maintained HTTPS reverse proxy with rate and concurrency limits. An HTTP reverse proxy is not a wrapper for a raw TCP protocol — tunnel those over VPN or a proper TLS/auth layer instead.
  • Restrict admin and SSH to management networks, disable UPnP, run services unprivileged, update dependencies, and clamp tuning to approved ranges.
  • Validate every user-supplied frequency/sample-rate/mode with strict numeric range checks. Never concatenate user input into shell commands — use fixed executables and argument arrays, or a narrow internal API. No arbitrary command execution from the web UI.
  • If receive-only, physically remove or disable transmit/PTT paths so remote controls cannot key a transmitter.

Correction to a common assumption

A "Bitcraze fork" of gr-lora could not be verified. Bitcraze's organisation focuses on the Crazyflie; the Bastille README credits Matt Knight's blind signal analysis, and jkadbear/gr-lora describes itself as developed from Matt Knight's gr-lora. The "BastilleResearch/Bitcraze fork" attribution appears to conflate separate projects.

The hard part: concentrated vs. parallel reception

LoRaWAN's uplink channel plan is the reason a single configurable decoder is not a gateway. Semtech's SX1302 lists eight 125 kHz channel packet detectors, eight SF5–SF12 demodulators plus additional SF5–SF10 demodulators, with 125/250/500 kHz demodulation. An SDR flowgraph must instead instantiate parallel decoders per channel and SF, and every extra branch costs CPU.

The missing piece

No maintained, general-SDR-decoder → Semtech UDP / Basics Station → ChirpStack or TTN bridge was found. Decoding a radio frame and implementing a gateway's network protocol are separate jobs: gateway messages carry frequency, data-rate/SF/BW, RSSI, SNR, size, timestamp and gateway identity, plus downlink handling. Projects that come close are not that bridge — Helium's lorawan-sniffer parses and mirrors Semtech UDP traffic from an existing forwarder (it does not demodulate IQ), Povalac's sniffer uses SX1301 concentrators, and EPFL's gr-lorawan is an SDR transmitter (its USRP uplinks were received by TTN). Treat SDR→ChirpStack as a custom adapter project, not an off-the-shelf integration.

What SDR is genuinely good for here: passive monitoring

  • Spectrum and waterfall — spotting bursts, channel occupancy and interference. PentHertz's walkthrough (USRP B205mini) scans, identifies an 868.2 MHz / 125 kHz signal, tries SF settings, decodes with gr-lora and feeds Scapy tooling; it notes an RTL-SDR-class receiver also works, with performance caveats.
  • SF/BW usage, airtime and duty-cycle estimates — log packet start/end plus decoded PHY parameters and length. A waterfall alone shows energy, not a reliably identified LoRa transmission or a regulatory category.
  • RSSI comparison against the gateway — only meaningful on the same packet after calibrating antenna, cable path and gain. An SDR's dBFS is not automatically a gateway's dBm.
  • Real precedents: LoRadar (2020) is a passive sniffing framework reporting collision/jamming detection, localization and duty-cycle policing; Povalac et al. (2023) ran long-term multi-city captures — and did so with three SX1301/iC880A concentrator modules on a Pi, not an SDR, precisely because simultaneous channels, both chirp polarities, RX2 and Class-B beacons are demanding. Open hardware, code and a Zenodo dataset exist.
  • Benchmark for the honest comparison: RSSI-fingerprinting research (Pretoria, 2024) reports ~285 m mean error — concrete, and a reminder that localization is not room-level from one SDR.

A sensible monitoring station

Raspberry Pi 5 + RTL-SDR Blog V4 (1 ppm TCXO, HF upconverter; ~2 MHz usable) or Airspy Mini (12-bit, 0.5 ppm) + a sub-GHz antenna + GNU Radio/gr-lora_sdr decoding one channel, logging timestamp, channel/SF/BW, CRC result and calibrated power. Use rtl_tcp or SoapyRemote for remote IQ access, and OpenWebRX+ separately if a browser waterfall helps. Feed it from a separate antenna or a careful RF tap — do not interrupt the operational gateway's antenna feed.

Pitfalls

  • DC spike / IQ imbalance on RTL-SDR: avoid parking the LoRa channel at exact centre, or enable DC/IQ correction (SDRangel exposes both; SDRangel's remote-TCP input warns that empty input buffers mean insufficient network bandwidth and growing output buffers mean the CPU cannot keep up).
  • Clock accuracy: gr-lora_sdr includes CFO/timing estimation, but do not assume every dongle is equal — measure and trim, and watch decoder frequency offset.
  • Sample rate: Nyquist minimum is the channel bandwidth; practical chains oversample. SDRangel's LoRa path oversamples ×2, implying ~250 kS/s for 125 kHz and ~500 kS/s for 250 kHz (implementation-specific).
  • Storage: raw complex IQ at 2.4 MS/s is ~4.8 MB/s at 8-bit I/Q and ~9.6 MB/s at 16-bit — decide retention deliberately.
  • Regional span: EU868's 125 kHz channels fit a narrow slice; US915's full 902–928 MHz is 26 MHz and cannot be seen by one RTL-SDR-class capture.

Meshtastic / MeshCore are a different animal

These are LoRa-based mesh protocols, not LoRaWAN, so LoRaWAN decoders and bridges are the wrong tool. SDRangel ships Meshtastic and MeshCore demodulator plugins (MeshCore README documents an optional UDP JSON sink and EU_NARROW defaults of 869.618 MHz, 62.5 kHz, SF8, CR 4/8; the Meshtastic plugin is labelled experimental and recommends dedicated hardware for production). alphafox02/meshtastic-sniffer is a substantial passive receiver with RTL-SDR/Airspy/USRP/HackRF/BladeRF/Soapy backends, wideband channelization, JSON/MQTT/ZMQ/pcap outputs and a dashboard. Jeff Geerling's Pi 5 write-up is a useful reality check: he got PHY activity on a narrowed RTL-SDR flowgraph, but the included Python RX decoding script was not working in his test.

Assessment of the proposed LoRaWAN architecture

The plan — sensors → gateways (Pi + RAK2245) → internet → self-hosted ChirpStack on Hetzner, gateways managed by balenaOS/openBalena, long-term goal of also providing TTN coverage via a packet multiplexer — is sound in its core. Two specifics need correcting before it is presented.

Proposed Sensors → GW (Pi + RAK2245) → UDP 1700 → Hetzner / ChirpStack
Long-term GW → Packet Multiplexer → ├ private ChirpStack
└ TTN ← UDP only, no Basics Station

ChirpStack: what to run

  • Version: the 4.x series is current (releases page showed v4.19.2 "Latest" and v4.20.0-test.3 pre-release when checked). v4 merges the Network Server and Application Server into the main ChirpStack service; the Gateway Bridge is a separate service. Sources that mention a standalone "chirpstack-network-server.toml" are describing the legacy v3 layout — worth knowing, because Packet Broker's own ChirpStack guide still uses that legacy naming (see below).
  • Components: ChirpStack + Gateway Bridge, plus PostgreSQL 13+ (needs pg_trgm), Redis 6.2+ (or Valkey) for sessions/metrics/cache, and an MQTT broker (Mosquitto) — docs call for MQTT 5.0 and shared subscriptions. Gateway-side extras exist but are optional: Concentratord (ZeroMQ API) and ChirpStack MQTT Forwarder, which the project now calls its preferred gateway installation over the legacy UDP bridge.
  • Install: official Debian/Ubuntu apt packages or the official Docker Compose example. Note the Compose repo itself warns it is a testing starting point, not production-ready unchanged.
  • Sizing: there is no official sizing table and no hard device/gateway ceiling. Two vCPU / 4 GB may carry a modest low-rate private deployment; 4 vCPU / 8 GB with SSD is a conservative starting point (Helium's guide cites exactly this and explicitly says it is not recommended for mission-critical production). Practical capacity depends on message rate, gateway count, integrations and retention — not registered device count.

Flaw 1 — the packet multiplexer cannot do Basics Station

Why this breaks the long-term goal as written

chirpstack-packet-multiplexer accepts Semtech UDP only and forwards to multiple servers, with an uplink_only flag per destination and optional gateway-ID / DevAddr / JoinEUI prefix filters, plus Prometheus metrics. It is not a general LoRaWAN backend broker.

A 2024 request to add Basics Station support was closed: the maintainer said there was no current bandwidth, and that Basics Station obtains its configuration from its LNS, so different LNSs may not share a usable configuration. So if the gateways move to the modern Basics Station path — which is exactly the plan — the multiplexer is out.

Two further caveats even on UDP: multiplexing copies traffic, it does not synchronise device sessions, join state or network policy between the two networks, so you must decide which backend is authoritative for downlinks (the uplink_only flag exists for this). And Semtech UDP is the legacy option — The Things Stack warns about its security and scalability and recommends Basics Station instead; avoid exposing an unauthenticated UDP 1700 listener to the public internet.

What Basics Station actually is

LNS is the data path: gateway and network server exchange uplinks and downlinks over WebSocket; the protocol first discovers an endpoint (muxs) and its URI. That endpoint discovery is load assignment, not a mechanism for copying traffic to multiple independent LNSs. CUPS is optional management (config and firmware updates, and it can deliver LNS credentials) and is not required for LoRaWAN traffic. ChirpStack's Gateway Bridge does implement the Basics Station LNS protocol — and its docs warn that without authentication all connections are accepted, so configure TLS.

Consequence for the plan: "gateway also provides TTN coverage" is achievable, but not by bolting a multiplexer onto Basics Station. The realistic options are (a) keep the dual-backend gateways on Semtech UDP and multiplex, or (b) have gateways natively support multiple backends or run two forwarding processes, or (c) peer networks properly via Packet Broker. Option (c) is the architecturally clean route and is discussed next.

TTN / The Things Stack: limits and Packet Broker

  • Sandbox/Community is described by TTI as free, limited, without SLA, and intended for non-commercial small-scale testing. The documented Fair Use Policy is 30 s uplink airtime and 10 downlinks per device per 24 h — these are airtime/downlink limits, not a device-count cap. No fixed numeric device cap could be verified.
  • Does contributing a gateway lift the limit? No official source says so. TTN encourages gateways for coverage; it does not promise extra airtime or downlinks in return. Treat it as helping coverage, not as an allowance increase.
  • Packet Broker is network-to-network peering: forwarder networks (with gateways) and home networks (with devices), routing uplinks by DevAddr/NetID with policies for joins, MAC and application payloads, metadata and downlink direction. That is roaming/peering — not the same as pointing one gateway at two servers.
  • Can self-hosted ChirpStack peer with it? Protocol-wise yes — Packet Broker documents LoRaWAN Backend Interfaces 1.0 support and publishes a ChirpStack configuration guide, including requesting a NetID (and optionally a tenant ID), exchanging credentials/certificates, and configuring the roaming endpoint; it even describes requesting free access to forward to TTN Community.
  • Two qualifications: (1) the Sandbox does not let its users define their own Packet Broker routing policies — the Foundation controls peering; (2) the Packet Broker ChirpStack guide uses legacy config naming, so a current tested ChirpStack v4 recipe and current approval terms were not verified. Confirm with Packet Broker before designing around it.

balenaOS / openBalena for the gateway fleet

  • openBalena still exists and is self-hosted (provisioning, CLI management, remote VPN access, image distribution, container updates; README requires balenaOS ≥ v5.2.8 and balena CLI ≥ v18.2.2). But the project calls itself beta — "perpetually in beta" — with potential breaking changes, no web dashboard, single-user management and full-image rather than delta updates.
  • It is self-hosted software, not a free hosted tier. No device-count limit is stated for self-hosted openBalena because you operate the infrastructure yourself.
  • balenaCloud free allowance is 10 devices total across fleets; beyond that is paid.
  • Containerised updates: a release is one or more images; deploying notifies the fleet, which downloads and runs per the chosen strategy (balena push/balena deploy; git push is legacy).
  • The radio detail that trips people up: the application needs a packet-forwarder/Basics Station build plus the matching concentrator HAL/driver — SX1301 for RAK2245, SX1302 for RAK2287. Gateway Bridge is not the HAL. balenaOS enables SPI by default on Pi and documents container device access/privileged mode. Verify the exact concentrator revision against the image you deploy.
  • Alternatives: Ansible is a strong lightweight choice for a modest Pi fleet (inventory, OS packages/services, version-pinned config, staged rollouts). Mender adds A/B root-filesystem OTA with rollback at more setup cost. Docker Compose + CI with pinned image digests works well. cloud-init helps first-boot provisioning but is not an update service. Do not use Watchtower for a new production fleet — its own repo says it is no longer maintained and recommends against production use.

A revised recommendation

Keep the good parts, fix two things
  1. Keep the private ChirpStack on the Hetzner VPS — that is the right call for escaping TTN's fair-use limits. Go with the apt packages or a de-Dockerised Compose, PostgreSQL + Redis/Valkey + Mosquitto, 4 vCPU / 8 GB SSD to start, and set up backups and monitoring from day one.
  2. Change the gateway protocol decision consciously. If dual-backend fan-out is a firm requirement, the gateways must stay on Semtech UDP with the packet multiplexer — accept that this is the legacy, unauthenticated path and keep it off the public internet (VLAN/VPN). If you want Basics Station (recommended for security and manageability), then drop the multiplexer and use Packet Broker peering for the TTN direction.
  3. Reframe the long-term TTN goal from "our gateways also feed TTN via the multiplexer" to "our network peers with TTN via Packet Broker, and/or we operate separate gateways or forwarding processes." Verify the ChirpStack v4 + Packet Broker path with the operator before committing it to a slide.
  4. Reconsider openBalena. For a small fleet, Ansible with pinned container releases is less platform risk than a self-hosted beta. If you use balena, prefer balenaCloud while the fleet is within 10 devices, or accept operating openBalena in beta.
  5. Add the SDR as a diagnostic, not a gateway. A Pi 5 + RTL-SDR V4 (or Airspy Mini) with gr-lora_sdr on a separate antenna gives independent spectrum/waterfall monitoring, SF and airtime measurement, duty-cycle evidence and interference diagnosis — genuinely valuable for a research institute, and honest about the fact that it is not a gateway.

Open questions to resolve before the presentation

  1. Which ChirpStack version and install path exactly, and who owns backups, upgrades and monitoring on Herr Scherl's server — the plan relies on someone else's capacity, which needs a written arrangement.
  2. Basics Station or UDP for the gateways. This single decision cascades into the multiplexer question, the security model and the TTN integration route. It should be made explicitly, not left as "to be verified".
  3. Packet Broker access terms for a self-hosted ChirpStack in 2026 (§ 3 of this report). Verified only at protocol level and via a legacy-layout guide.
  4. Whether a public remote SDR is even in scope, and if so which bands. If yes, this triggers the § 5 TDDDG and GDPR work, and possibly a DPO/DPIA decision. If the SDR is internal-only for monitoring, that entire legal section drops away.
  5. Gateway firmware/HAL reality: confirm the exact RAK2245 revision (SX1301) and that a maintained packet-forwarder/Basics Station build exists for the balena image you intend to ship.
  6. Device and traffic scale: how many sensors, what payload size and interval. This, not the sensor count, is what sizes the VPS and sets database growth.
